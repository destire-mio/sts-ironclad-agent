# 商店删牌的结算时机与库存检查

本轮使用 24 个独立原版场景、127 个检查点，证实四个商店删牌时机反例。修复后生产与观察构建的行为比较字段吻合，53 处规则字段分歧消失；四个场景中的九处药水动作列表差异保留。参考为安装的 Java 游戏及 Mod，完整一致性为 `INCOMPLETE`。

## 反例与修复

购买星系仪、领取两份卡牌奖励、回到商店，留下三份奖励。此时购买删牌服务并确认选择，原版关闭选牌界面后恢复奖励页，牌组、金币及删牌服务保持原值。返回商店时，原版 `ShopScreen.updatePurge()` 扣款并移除选中的牌。旧模拟器在确认选择时执行扣款与移除，导致奖励页中的牌组和金币出现分歧。

四个反例覆盖普通删牌、删寄生、领取剩余奖励至空、从升级与未升级的重复牌中选择一张。寄生的生命上限减少发生在返回商店时。取消删牌、没有剩余奖励时的删牌及寄生移除作为对照。

修复在 `GameContext::chooseSelectCardScreenOption` 中复用返回回调：商店选牌后若进入奖励页，保存选择和回调的值，等返回商店时结算；没有剩余奖励时完成结算。非商店移除路径保持其行为。回调恢复商店的退出动作，避免重复扣款；副本持有自身的选择与返回回调。补丁没有增加持久状态字段。

上一轮 native 定向测试曾把“确认即扣款”写成断言，缺少原版删牌流程证据；本轮依据原版检查点修正该断言。旧源码、旧测试输入和旧二进制保留在 R10 冻结目录。

## 其他库存场景

蛋类遗物购买后对应类型的库存升级、购入卡牌的升级状态、陶瓷小鱼的金币及后续可购动作、无色牌的快递员补货和折扣、普通药水购买、背包满后的丢弃与购买、添水限制，以及存钱罐失效的比较字段吻合。初始库存由两端使用相同的声明输入；本轮不覆盖自然生成商店库存。

原版 CommunicationMod 会列出付得起的药水，即使药水槽满或持有添水。native 合法动作排除这些点击。报告保留原始动作列表差异；对这四次点击，native 观察器调用公开 `Shop::buyPotion` 防护分支，验证所检查的钱包、背包、库存和十组 RNG 没有变化。这不代表 native 接受了对应 `GameAction`。

分类器要求药水槽满或添水存在、两端钱包／库存／背包／遗物相同、全部非药水动作相同，且被省略的药水动作恰好对应库存中付得起的槽位。错槽位、少动作或错误后态均不能归入该分类。

## 原版采集修正

初次试跑的两例卡在通信通知：`hasControl` 的初值为真，其清除逻辑属于战斗更新；已完成的商店界面可以保留该值。商店选牌确认还会阻塞 CommunicationMod。复制到隔离实例的观察器在 `inventory_audit` 场景中检查动作、卡牌、怪物及回合前队列为空，没有活跃动作、用牌、淡入淡出或待处理逻辑效果后，通知通信插件。它不修改牌组、金币、生命或 RNG。奖励页上的待删牌操作依赖下一次玩家输入，不能当作此时必须完成的动作。

三个补充小牌组缺少瓶装烈焰的生成条件，原版拒绝了初态。修正场景中的未购买库存遗物为可生成的纸蛙后，使用新 JVM 重跑。五份失败捕获、对应输入和重试来源保留；失败捕获没有作为规则比较结果。

一份旧星系仪／瓶装遗物场景用修改后的观察器新开 JVM，原版命令、初始池与所投影状态和旧捕获相同。观察器修正及失败分类见[记录](../../runs/parity-20260928/round29-shop-inventory-tools/capture-corrections.json)和[原版回归对照](../../runs/parity-20260928/round29-shop-inventory-tools/legacy-control.json)。

- 456 个 CTest 入口通过；新增八项 native 定向测试，旧运行时五项失败、三项对照通过。103 个 native 动作检查父副本隔离及执行结果。
