# 搜索机制审计

## 预算语义

`playoutReusing` 把 Boss 的预算设为 `simulations * bossMultiplier`。所以心脏 80000×12 为首轮 960000 次；首轮没有胜利路线时，combat4 系列继续同一树、同一搜索 RNG 再搜索一个预算。后续轮次：已有胜利见证时用预算的四分之一，否则用 1.5 倍。`boss_multiplier` 是预算倍率，不是胜负估值权重。因此 Heart 上 160000×12 与 80000×24 的有效预算相同，无需重复算一遍。

来源：`../sts-rl-agent-combat4q/agent/combat_search_reuse.h:29-75`。本研究实际调用次数、模拟次数与 process_time CPU 秒保存在每个结果行。

## 固定策略与 RNG

每个状态/策略调用一次 resolver；源状态由记录前缀重放，所有对照记录同一 `root` 指纹和游戏 `rng`。搜索随机数在构造函数用 `bc.seed + bc.floorNum` 初始化；没有换游戏种子，没有随机重启挑结果。combat4 内部继续同一树属于固定预算调度。不能把各候选在每局中的最高分组合成部署策略。

Linux 的两个 pilot 基线逐动作复现历史记录；macOS 对相同开局指纹与游戏 RNG 给出不同搜索序列。因此正式 effect 计算使用同平台的 base/candidate，历史 win 只用于分层采样。差异的具体浮点/标准库来源没有在本任务中定位。

## 输出上限、状态牌与药水

A20 Heart 源码设置 Invincible=200，Beat of Death=2；Blood Shots 基础 2×15。DEBILITATE 插入 DAZED/SLIMED/WOUND/BURN/VOID；CardManager 的 draw 分支包含 Evolve 额外抽牌与 VOID 失去能量。没有观察到这两个机制缺失。

c38 147 个心脏败局中 146 局最后没有药水，1 局剩 SMOKE_BOMB。此证据不支持把“有用药水一直不用”作为主要根因，但不排除喝药时机错误；完整时序可在 traces 中核对。

有 20 个败局在 Invincible 余量为 0 时出过攻击牌。攻击牌可能触发抽牌、力量、格挡与遗物，不能把全部此类动作删除。有限搜索未找到胜线时，其失败终局评分仍包括伤害、能量浪费、抽牌量、存活回合。固定推演策略中，手里有可打牌时 END_TURN 采样权重约为其它动作的十分之一，可能不利于封顶后收手，但这只是源码支持的候选解释。

## 本次推演对照的边界

`rollout3` 采用已有 `resolve_combat3`：它同时改变专家排序混合比例、预算续搜和药水策略，因此不能把其差异单独归因于出牌顺序。增加只针对心脏的封顶/防御推演规则需要新的 C++ 运行包和独立对照；本研究不把源码推断当作实测收益。

## 速度药水的机制反例

`potion-timing-diagnostic.json`：seed 3900012947，三条分支从同一个 Heart root 开始，后续保持原记录动作。原线 T7 死亡，Heart 280 HP；删去 T1 Speed Potion 后仍 T7 死亡、Heart 280 HP，整条动作合法；把该药固定移到 T2 起手，原序列执行结束为 T8、玩家 6 HP、Heart 270 HP、UNDECIDED。后者没有完成心脏战，不记为胜利或救回。这是药水时机存在改进空间的机制证据，不是部署策略收益证据。

## 搜索开销与失败边界

开发集 3900012623 带 Gambling Chip，h160 用 563.46 CPU 秒、3840万模拟，h320 用 956.45 CPU 秒、7680万模拟，二者均败。更大的节点预算会放大选牌分支和反复规划成本；它不是 CPU 时间上限。采样文件 tail-search-active-sample.txt 显示搜索/动作计算活动，没有据此认定死锁。进程生命周期内的峰值内存不能归给单场战斗。

3900012803 的本机基线无胜利见证，1344万模拟后败；减半预算以276万模拟胜出，终局10HP。这不意味着少搜必然更好：预算改变尚无胜线时选择的前缀，继而改变后续状态和探索。搜索输出的可执行终局与状态指纹通过后，才能排除“搜索报告胜利，执行却死亡”这一类错误。

## 商店中的机会成本

预定药水优先规则在48个根上救回1局、损失4局。3900012255 初始130金币，基线先买84金币的 Dark Embrace；候选先买110金币的 Fairy Potion，余20金币不足以购买该牌。两线进心脏均40HP、0药水，基线胜、候选负。药水的历史携带胜率高，不能推出它应该挤掉关键引擎牌。

其它分歧的首动作：3900012494，准备背包对虚弱药，候选救回；3900012772，工具箱对虚弱药，候选损失；3900012087，医疗箱对敏捷药，候选损失；3900012879，铜制鳞片对能力药，候选损失。它们是整个固定购置规则的后续终局对照，不是孤立物品的通用排序。

后期选牌分叉 3900012776：基线后缀17.05 CPU秒，候选1177.28 CPU秒，候选合计370880000次模拟，二者最终死亡。候选不是超时/故障，等待其终局后纳入统计。采样 prep-tail-sample.txt 显示 UCT 树选择及 log 计算；不能据此把某张牌认定为性能根因。combat4q 的256轮重规划上限意味着入口80000不是整场80000，也不是CPU时间预算。

## 可验证的下一组搜索改法（本次没有计入收益）

1. 临时敏捷药：在当前状态没有可执行格挡增益、也没有人工制品可保留敏捷时降低喝 Speed 的推演优先级；T2/3可兑现格挡时恢复。不是禁止T1用药：T1格挡可以抵销死亡律动，人工制品也能改变药效持续。以2947为机制反例，再用新根的固定策略对照检验终局。
2. Invincible余量为0时，提高 END_TURN 相对于纯伤害牌的推演权重；保留含抽牌、格挡、消耗、力量、回血及遗物触发价值的攻击。仅在推演采样里改权重，保留树中所有合法动作，避免把可赢路线剪掉。用2175、2025审计格挡来源，再以新根的救回/损失验收。
3. 未找到胜利见证时的失败评估，按存活/防御缺口检验抽牌数、出牌数和“能量浪费”项是否诱导无收益出牌。先做单项等预算消融，不把combat3的多项差异解释成某一评分项的收益。

以上需要新的本机隔离C++运行包。本任务没有修改云端正在用的运行包，也没有把未完成的药水时机分支算为胜利。新候选需在调参前冻结规则与新留出根；本次留出结果不能反复用于调参后宣称独立确认。

2175 的另一个可检验点：T6 Feel No Pain=3、Beat of Death=2。仅看“Reckless Charge出牌→Medical Kit打出其Dazed并耗尽”这两个动作，死亡律动成本4格挡，一次耗尽回3格挡，净消耗1格挡；这是忽略额外抽牌/自动施放/遗物的局部算例。封顶后过牌仍可能找到有效防御，所以不能据此硬剪所有此类循环，但失败评分按抽牌数给奖励时，应检查它是否鼓励这种净消耗循环。
